# 城市自来水爆管抢修停水通知与复供服务

## 原始需求

> 开发城市自来水爆管抢修停水通知与复供服务，可采用 Java、Spring Boot 和 PostgreSQL。管网传感器、居民报修或巡检员发现路面涌水后，服务根据管径、阀门分区、周边小区、医院学校、道路交通和历史管线资料判断影响范围。调度员派出抢修队时，需要同步阀门位置、开挖许可、交通协管、备件库存、预计停水时间和应急送水点。若爆管影响高层小区、餐饮街、学校午餐或医院透析用水，服务要把抢修队、客服、街道、物业、供水车和水质检测人员放在同一事件里推进。抢修过程中，现场人员记录关阀、开挖、换管、冲洗、消毒、压力测试和道路恢复。复供前，服务必须确认水压、水质、管网冲洗和用户通知；复供后，黄水投诉、二次漏水、道路沉降和赔付申请继续回到原抢修单，形成从报警到复供的完整记录。客服通知需要覆盖短信、电话、物业群、学校联系人和重点用户名单，通知内容要随抢修进展变化。对于长时间停水，服务还要记录临时水点排队、老人送水、商户停业损失和二次供水水箱状态，避免复供后仍有楼栋供水异常。

## 技术栈

- Java 17 + Spring Boot 3.3（Web / Data JPA / Security / Validation / Actuator）
- PostgreSQL 16（仅 compose 内部网络访问，不发布宿主端口）
- 前端：原生 HTML/CSS/JS 单页工作台（由后端静态托管）
- 交付：多阶段 Dockerfile（非 root 用户 + HEALTHCHECK）+ docker-compose 一键部署

## 一键启动（验证方式 = 宿主 docker compose up）

```bash
cp .env.example .env        # 可选，直接使用默认值亦可
docker compose up -d --build
```

- 应用端口通过环境变量 `CC_PUBLISH_PORT` 发布到宿主（见 `.env.example`，默认 3066），容器内固定 8080。
- 查看实际映射端口：`docker compose port app 8080`
- 浏览器访问：`http://localhost:<CC_PUBLISH_PORT>/`（未登录自动跳转登录页）
- 健康检查：`http://localhost:<CC_PUBLISH_PORT>/actuator/health`
- 停止并释放资源：`docker compose down`（加 `-v` 同时清空演示数据）

## 演示数据

首次启动自动初始化（可用 `SEED_DEMO_DATA=false` 关闭）：

- **管网基础资料**：3 个阀门分区（城东/城西/老城区）、4 段历史管线（DN600 球墨铸铁 1998、DN400 PE 2005、DN300 铸铁 1985、DN200 PE 2015）、6 个阀门、9 个重点设施（高层小区、人民医院透析中心、实验小学午餐食堂、美食街、道路等）。
- **事件一（抢修中）**：中山路 DN600 爆管，已评估+已派单+进度到开挖，已持续 8 小时触发长时停水预警，含送水点、老人送水、商户损失、二供水箱低水位记录；**人民医院应急供水保障单**已调度供水车并供水到位（车辆无法进院，已改设水点+志愿者送水），待医院确认。
- **事件二（已报警）**：滨河路居民报修，待评估 —— 用于演示「评估 → 派单 → 进度 → 复供」全流程。
- **事件三（已复供）**：老街 DN300 换管完成并复供，复供确认单四项齐全，挂有一条黄水投诉 —— 用于演示复供后问题闭环与事件关闭。

## 关键业务流（建议演示顺序）

1. **报警上报**：调度员在「爆管事件 → 新建报警」登记（来源：管网传感器/居民报修/巡检员）。
2. **影响评估**：事件详情点「生成影响评估」—— 系统按管径、阀门分区、周边小区/医院/学校/餐饮街、道路交通和历史管线资料自动生成影响人口、关阀方案、管线分析、交通影响、建议级别与预计停水时长。
3. **调度派单**：同步阀门位置、开挖许可、交通协管、备件库存、预计停水时间、应急送水点；按评估结果自动勾选协同方（抢修队/客服/街道/物业/供水车/水质检测），派单即自动生成首条停水通知。**门禁：开挖许可、备件库存、应急送水点三项必填，任一缺失返回 4xx 且事件保持「已评估」。**
4. **现场抢修**：抢修队按顺序逐阶段上报（到场→关阀→开挖→换管→冲洗→消毒→压力测试→道路恢复），不允许跳阶段或回退，保证时间线保留全部现场阶段；每推进一步，客服通知内容自动更新。
5. **复供确认**：水质检测员填写复供确认单（水压/水质/管网冲洗/用户通知 + 浊度/余氯）；调度员「确认复供」—— **必须已完成道路恢复**，且四项确认缺一即拒绝放行；门禁失败时工单与事件状态均不变化。全部通过则事件转「已复供」并自动发送复供通知。
6. **复供后闭环**：黄水投诉/二次漏水/道路沉降/赔付申请登记到原抢修单，受理→办结；全部办结后事件才能关闭。
7. **客服通知**：覆盖短信/电话/物业群/学校联系人/重点用户，模板内容随抢修阶段变化，目标人群按影响评估自动生成。
8. **长时停水保障**：临时水点排队人数、老人送水进度、商户停业损失申报与赔付、二次供水水箱水位状态，工作台对超 6 小时未复供事件红色预警。
9. **医院应急供水保障**：影响医院时派单自动建保障单，优先识别透析/手术/消毒供应/住院楼需求并带入医院后勤联系人；调度供水车与临时水箱 → 供水到位（到位时间、用水量写入事件）→ 医院确认；供水车无法进院时记录改设水点、志愿者送水与医院确认人，保障过程可写复盘；复供时间自动回写保障单；医院确认后事件列表/工作台/客服端均显示「医疗用水保障完成」，避免普通客服重复催问抢修队。

## 主要接口（REST，会话认证）

| 方法 | 路径 | 说明 |
|---|---|---|
| POST | `/api/events` | 报警上报 |
| POST | `/api/events/{id}/assess` | 自动生成影响评估 |
| POST | `/api/events/{id}/dispatch` | 调度派单 |
| POST | `/api/orders/{id}/progress` | 现场进度上报（阶段只能前进） |
| POST | `/api/orders/{id}/restore-check` | 复供确认单登记 |
| POST | `/api/orders/{id}/confirm-restore` | 复供放行（四项确认门禁） |
| POST | `/api/events/{id}/close` | 关闭事件（须复供且问题清零） |
| GET/POST | `/api/notifications` | 通知查询/手动发送；`GET /api/notifications/template` 模板预览 |
| GET/POST | `/api/issues` | 复供后问题登记与处理 |
| GET/POST | `/api/support/*` | 送水点 / 老人送水 / 商户损失 / 二供水箱 |
| GET/POST | `/api/hospital-support` | 医疗保障单查询/手动登记；`/{id}/dispatch` 调度供水车、`/{id}/supply` 供水到位、`/{id}/access-issue` 车辆无法进院、`/{id}/confirm` 医院确认、`/{id}/review` 复盘 |
| GET | `/api/dashboard` | 工作台看板 |
| GET | `/api/base/*` | 分区 / 管线 / 阀门 / 设施 / 枚举 |

## 项目结构

```
├── Dockerfile              # 多阶段构建：maven 构建 + temurin JRE 运行（非 root + HEALTHCHECK）
├── docker-compose.yml      # app + postgres（仅 app 发布宿主端口）
├── .env.example            # CC_PUBLISH_PORT / 数据库 / 演示数据开关
├── pom.xml
└── src/main
    ├── java/com/citywater/burst
    │   ├── config/         # SecurityConfig（表单登录+角色）、DataSeeder（演示数据）、CurrentUser
    │   ├── model/          # 17 个实体 + 14 个枚举
    │   ├── repo/           # Spring Data JPA
    │   ├── service/        # 事件评估 / 抢修复供 / 通知 / 复供后问题 / 停水保障 / 医疗保障 / 看板
    │   ├── web/            # REST 控制器 + 全局异常处理
    │   └── dto/            # 请求体与组合视图
    └── resources/
        ├── application.yml
        └── static/         # 登录页 + 单页工作台
```
